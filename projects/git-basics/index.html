01

第 1 幕 · 为什么要先学 Git

做 AI Demo、网页小作品或黑客松项目时，最怕的不是不会写代码，而是不知道自己刚刚改坏了哪里。

最常见的项目事故通常长这样：改到一半页面坏了，不知道刚才动过哪里；文件夹里出现 final、final2、真的 final，但没人知道哪个能交；队友发来新版代码，你自己的修改被盖掉；接 API 时不小心把真实 key 放进公开仓库；让 Agent 大范围改文件，结果坏了以后不知道怎么退。

从手工版本到时间线

📄

手工版本控制

版本散在文件名里，靠记忆猜：final.html、final2.html、真的final.html、不要动这个.html。问题是：哪个能交？谁改过？差在哪？坏了找谁？

⏱

Git 版本控制

变化进入时间线，每一步都有说明。你可以比较差异、回看历史、找到安全点，而不是在一堆文件名里猜。

最短工作流地图

阶段你现在要做什么Git 动作产出
拿到项目先跑起来，确认起点没坏新建或确认仓库项目开始有历史线
完成小功能页面能打开，功能能点commit一个有名字的存档点
准备大改接 API、改首页、换视觉开 branch一条安全试验线
想给别人看本地已经能跑push云端展示和协作版本
改坏了先停手，不乱删看历史和差异找到能求助的证据
交付前检查隐私、密钥、说明交付检查能安全展示的版本
课堂只学这条最短路线：拿到项目 → 小步提交 → 开试验线 → 推到云端 → 改坏救命 → 交付检查。先能活下来、能协作、能展示，再慢慢补命令细节。
02

第 2 幕 · 仓库、commit 和 push

仓库是历史盒子，commit 是有名字的存档点，push 是把本地历史同步到 GitHub。

什么时候新建仓库

仓库可以理解成“这个项目的历史盒子”。一个项目一旦进入仓库，后面的变化就可以被记录、比较和回看。

✅

适合新建仓库

你已经有一个项目文件夹，接下来会连续改它；准备让 Agent 帮你改代码；准备和队友协作；希望最后把作品放到 GitHub 展示。

⏳

可以先不建仓库

只是临时下载一个文件看一下；只是一次性写几行草稿；这个文件夹混着很多无关材料，还没整理出项目边界。

判断口诀：如果这个文件夹会变成你的作品，就让它尽早进入仓库。

Commit 是存档点，不是交作业

Commit 可以先理解成一次有名字的项目存档。更好的节奏是：完成一个小目标，确认它能跑，再存档。

好

适合 commit 的时机

页面终于能打开；新增了一个完整 section；修好一个明确 bug；完成一次可描述的视觉调整；准备让 Agent 或队友做大改之前；今天要收工，想把能跑的状态保存下来。

停

不适合 commit 的时机

项目还完全跑不起来；自己也不知道刚刚改了什么；文件里有真实 API key、token、密码或隐私信息；只是临时下载的大文件、缓存、依赖目录。

Commit message 是写给未来自己的线索

不够清楚好一点
update新增报名表成功提示
fix修复首页移动端按钮换行
final完成 Demo 展示页初版
111添加错题上传入口

Push 是把本地存档推到云端

Git 和 GitHub 不是一回事：Git 是电脑里的项目存档系统，GitHub 是云端展示柜和协作大厅。commit 是在自己电脑里保存一次历史，push 是把本地历史上传到 GitHub。

🚀

什么时候 push

已经 commit 过一个能跑的版本；想把作品备份到 GitHub；要让队友看到你的更新；要把项目链接发给老师、同学或评委；一天结束前想确保电脑坏了也不会丢项目历史。

🚧

什么时候先不要 push

还没检查有没有真实密钥；还没确认仓库是否应该公开；README 还完全看不懂；只是改了一堆混乱文件，还没 commit 成清楚的存档点。

03

第 3 幕 · Branch 是安全试验线

main 可以先理解成正式舞台，branch 是从主线拉出来的试验线。

什么时候开 branch

🧪

建议开 branch

接入 AI API 或支付、登录、数据库；全站换风格或重构首页结构；修一个不确定原因的 bug；队友同时在改另一块功能；让 Agent 做大范围文件修改。

🔧

可以不开 branch

改一个错别字；调整一句文案；改一个很小的颜色或间距；项目很小，而且你刚刚 commit 过安全点。

主线和试验线

main

稳定主线

最好一直保持能展示，随时可以给评委、同学或队友看。

feature

安全试验线

全站换风格、接 API、修不确定 bug，都先放这里试。试验成功就检查后合回，试验失败主线仍然能展示。

判断口诀：大改、危险、不确定，就开 branch。
04

第 4 幕 · 和 Agent 协作

Agent 一次可能改很多文件。越是让 Agent 做事，越需要小步提交和清楚边界。

小步提交让你敢和 Agent 协作

  • 1
    人先跑一遍项目

    确认当前版本能打开，不要从一个坏现场开始让 Agent 大改。

  • 2
    保存一个干净起点

    在大改之前先 commit，让你知道退路在哪里。

  • 3
    一次只给一个小目标

    不要一上来就让 Agent “重写整个项目”，先让它完成一个可验证的小任务。

  • 4
    改完先看文件差异

    看它改了哪些文件，再运行项目，确认行为没坏。

  • 5
    没问题再存档

    通过检查后再 commit，形成新的安全点。

让 Agent 带你做 GitHub 连接

Git 本身不需要注册。它是你电脑里的版本控制工具。你要注册的是 GitHub：一个放代码、展示项目、和队友协作的云端平台。

可以直接这样问本地 Agent：
我准备开始用 Git 和 GitHub 管理我的项目。请你一步一步带我完成本地电脑和 GitHub 的连接。我的电脑系统是【Mac / Windows / Linux / 不确定】，GitHub【已注册 / 还没有 / 不确定】，项目文件夹是【项目路径或项目名】。请先不要一次性给我一大串命令。每一步只让我做一个动作，并解释这个动作在解决什么问题。最后帮我验证这台电脑能不能把一个测试项目安全推到我的 GitHub。如果过程中需要我复制终端输出，请先告诉我哪些信息不能贴出来，例如 token、API key、密码、真实路径里的隐私信息。
05

第 5 幕 · 救命流程与密钥安全

项目坏掉时，第一步不是乱删文件夹，也不是复制网上的危险命令。先停手。

改坏以后，先别慌

1

停手

不要乱删，不要连续尝试高风险命令。

2

看 status

确认现在在哪个项目、哪条分支、哪些文件刚刚被改过。

3

存证据

保存截图、报错、终端输出，找到最近一次安全存档。

4

先解释，再执行

让老师或 Agent 先说明风险和方案，确认哪些修改要保留，哪些可以丢，再选择最小风险恢复动作。

红线：不要把 reset --hard 当成默认救命按钮。它可能直接丢掉未提交修改。压力越大，越要慢一步。

不要把钥匙提交上去

API key、token、密码、私钥都属于 secret。它们不是普通配置，而是能调用服务、花钱、读数据的钥匙。如果真实 key 已经 push 到 GitHub，通常要当作泄露处理：废掉旧 key，重新生成新 key。不是把文件删掉就结束，因为历史记录、缓存、别人 clone 的副本里可能还留着。

🔒

不能提交

真实 API key、token、密码、私钥；真实 .env；后台截图、账号截图、带手机号或真实地址的截图；大型缓存、依赖目录、临时文件。

📝

可以提交

.env.example、README 变量说明、占位配置示例、帮助别人理解项目的说明文档。

提交前 30 秒检查

检查你要确认什么
文件我知道哪些文件改了
内容我知道这次具体改了什么
secret没有 key、token、密码、隐私信息
README别人知道怎么打开或理解这个项目
最后用一句话收束：我知道我要提交哪些文件，看过这次改动，没有把钥匙、隐私和大垃圾放进去，这次提交说明也能让未来的我看懂。
